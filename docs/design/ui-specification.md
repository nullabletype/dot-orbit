# UI specification

The historical `prototype/index.html` remains useful exploratory evidence. This document records the product-level UI decisions that survived the design conversation; [`style-guide.md`](style-guide.md) is the detailed authority for component anatomy, visual states, accessibility and Avalonia reuse.

## Recommended direction

**Workbench** is the current recommendation. It uses:

- a persistent navigation rail;
- a primary working canvas;
- a contextual inspector for direct editing; and
- a dense but calm desktop information hierarchy.

Canvas and Ledger remain useful comparison directions in the prototype. They are not implementation commitments.

## Visual language

- Dark uses a near-black background with layered charcoal surfaces; Light uses warm near-white surfaces with the same hierarchy and density.
- Hot pink is the primary interactive accent.
- Green is reserved for completion, progress, and positive state hints.
- Category and Project colours come from a sixteen-key checked-in identity palette and provide local identification without becoming global status colours. The original eight keys remain stable for existing workspaces; Project defaults use an offset sequence to reduce immediate Category/Project clashes. Names remain canonical and visible; colours never encode status or behaviour.
- Rounded corners are restrained in Workbench, softer in Canvas, and nearly square in Ledger.
- Main copy should remain readable at normal desktop distance; metadata is visually quieter but not hidden.

## Navigation

1. Today
2. Upcoming
3. Backlog
4. Projects
5. Categories
6. Completed
7. Archive

Today is both the first item and the launch view.

Before the main workspace opens, the access window shows the selected local path in a wrapping, politely announced location panel. Native, keyboard-operable actions choose any existing file or a destination for a new workspace; the `.orb` suffix is suggested for discovery but is never a picker filter or validation shortcut. The first-run or unlock form follows the explicit choice. If the last successfully opened path is missing or unavailable, credentials and creation are blocked while Retry, Choose existing, Set up new workspace, and Use default location remain available. Errors are assertively announced without exposing passphrases, migration recovery paths, or other sensitive storage details.

The platform chooses the display and position for the unpositioned main workspace window. After unlock, the main window opens in normal state using its last accepted normal size in logical desktop units, or the existing 1180×760 default when no valid preference or screen information is available. The restored size is constrained to the associated display's usable working area, with the primary display as fallback. The supported 1120×600 minimum remains in force when the working area can accommodate it; on a smaller display, only the constrained runtime minimum axis is lowered to keep window chrome, navigation, and scrollable work surfaces reachable. Maximised, minimised, fullscreen, and scaling-transition dimensions are transient. Only an accepted main-window close remembers the final normal size, after save/discard/stay handling and pending Workspace writes complete; auxiliary windows and rejected closes do not change it, and preference failure never blocks shutdown.

Today presents persistent incomplete membership in **Planned** and **In progress** lanes, followed by Tasks completed on the captured current local date. Its New Task action opens a draft already assigned to Planned and lets the user keep it standalone or select an optional Project before creation. Today rows retain the shared Task-row anatomy: reorder and completion lead, title and Category remain central, due-date metadata is right-aligned, lane action and position follow, and the star is the final trailing action. The outlined star adds to Planned and the filled star removes from Today, with matching toggle state and accessible action text. Lane movement is explicit and does not imply a durable Task status. Clear Today removes all incomplete membership after a deliberate action; completion clears membership, and reopen returns the Task to Backlog without restoring it. Lane-local drag and accessible reorder actions update the relative shared order of the visible lane Tasks while preserving every hidden Task position.

Upcoming displays a badge counting incomplete, non-archived Tasks that are overdue or due through the end of the same weekday next week. The view contains Tasks only and groups Overdue first, then Today, Tomorrow, and subsequent dates. Overdue Tasks are oldest first; Tasks sharing a date retain shared Backlog order. Upcoming is not manually reorderable, but its rows support editing, completion, and Add to Today. Project target dates remain on Project surfaces. This accepted decision postdates the current HTML prototype and is not yet represented there.

Completed begins with an explicit bulk-archive control. It offers every whole-day threshold from 1 through 30, states the current affected Task count, disables the action when that count is zero, and requires confirmation before archiving. Age uses the captured local completion date with a strict older-than boundary. The action never archives Projects.

Projects expose an explicit compact Archive action on each Project header. An archived Project leaves Projects, Categories, Backlog, Upcoming, Completed, and Today as one aggregate without changing Task completion or individual Task archive state. Archive groups Project and Task entries by their captured local archive dates, labels Project entries distinctly, and offers accessible Restore actions. Restoring a Project returns eligible incomplete Tasks to Backlog while leaving Today empty and retaining any individually archived Tasks.

Bin is a secondary utility item at the bottom of the sidebar, visually separated from the seven primary views. Its count appears only while non-empty. The Bin view orders removed items newest first and contains per-item Restore actions and the confirmed Empty Bin action.

## Ordering interactions

- A six-dot handle communicates draggable rows and sections.
- Today and Backlog expose the same Task order.
- Projects exposes an independent Project order.
- Expanded Project subtasks expose their own per-Project order.
- Category headings expose an independent Category order.
- Within each Category, Projects and standalone Tasks appear in separate sections. Projects retain global Project order and standalone Tasks retain shared Backlog order; neither section adds a category-local order.
- Drop position opens a full labelled placeholder at the exact before/after boundary. Its text identifies the dragged item and destination position; its accent outline and tinted surface provide a second cue. Task placeholders match the source row height; Project and Category placeholders use heading height, including when expanded. The source retains its footprint with reduced opacity until drop.
- The pointer selects before or after a row using its heading midpoint. The top boundary appears above the first item, and the bottom boundary follows the complete last item. Moving inside an opened placeholder preserves its boundary. Reordering commits once on a valid release; preview leaves all order untouched. Escape, invalid or outside release, capture loss, deactivation, scrolling, resizing or a changed projection cancels the gesture. Existing keyboard reorder menus, restored handle focus and completion announcements remain available.
- Every reorderable item exposes Move up, Move down, Move to top, and Move to bottom through an accessible action menu scoped to the current list.
- Optional shortcuts such as Alt+Up and Alt+Down may accelerate reordering, but the action menu remains available and the new position is announced to assistive technology.

## List-row interaction contract

Current list surfaces compose the same semantic row states rather than defining surface-specific hover, completion, disclosure or reorder treatments. The authoritative row rules, component anatomy, semantic class names, state matrix and regression expectations are in the [desktop UI style guide](style-guide.md#rows-and-titles).

Every Task, Project, and Category heading in Today, Upcoming, Backlog, Projects, Categories, Completed, Archive timeline and search, Bin, and the inspector places one small shared work-type icon immediately beside the title. Tasks use a neutral task-card glyph, Projects use their coloured stacked work cards, and Categories use their coloured grid; Project and Category rows do not repeat a second identity marker on the secondary line. Project secondary context shows only the Category grid and name because Task progress already occupies the right-aligned metadata position. Category headings retain Project and standalone Task counts. Every Task row uses one compact segmented identity pill: Category first, then a straight one-pixel divider, then Project. Each segment's hover and pressed surface is rounded only at the capsule's outside edge and flat against the divider. The Category and Project glyphs carry their respective colours; standalone Tasks collapse the Project segment and divider into one fully rounded Category pill. On live Task surfaces each visible segment is a separate native button: Category selects Categories and scrolls and focuses the effective Category heading; an active Project selects Projects and scrolls and focuses the parent Project heading. The divider remains inside the Project button hit target rather than creating a dead seam. A jump aligns the complete containing row to the top of the viewport when enough content remains below it, keeping its frame and heading inset visible, while the end of the list clamps at the maximum scroll offset. An archived parent selects and targets its row in Archive because it is not present in Projects. The action uses the normal navigation guard and changes destination only after navigation succeeds. Category precedes Project in keyboard order. A Project in Bin keeps its visible segment disabled and out of keyboard order with restore-first guidance. Project-row and reference-window pills remain decorative. The pill stays aligned with the Task glyph edge, retains the visual 6px title gap, and leaves bottom clearance above the row divider. Archive and Bin Project rows keep Project identity beside the title and collapse the secondary pill to Category only. An attached Task that diverges from its Project Category retains the decorative fork in the Category segment and exposes `Category override` in the row accessible name. Existing dates, progress, archive/removal state, blocked restore guidance, and actions remain in their dedicated positions.

## Inspector

- Opens on row selection and keeps list context visible.
- Project and Task title, date, Category, Participant associations, and Markdown changes save automatically. Text changes use a 600 ms inactivity delay; discrete changes save immediately. A persistent status beside the inspector heading reports saving, saved, or failed and exposes Retry without requiring scrolling.
- An existing optional Project target date or Task due date remains selected and opens on its month. An empty date opens on the current local month with Avalonia's native today highlight while today remains unselected; opening and closing the calendar alone does not change or save the inspector.
- Navigating away, closing, or starting an immediate row action flushes pending valid Project or Task changes first. Invalid or failed changes remain in the inspector and block leaving until corrected, retried, or explicitly discarded. Category editing retains explicit Save and Cancel actions.
- Today membership, Planned/In progress, completion and Backlog/Today reorder actions remain keyboard-operable while ordinary action persistence is queued. Activations are accepted in order without optimistic row changes. The fixed top-bar status politely announces the number of pending changes, then the committed result or failure. A committed mutation whose projection refresh fails says that the change was saved and exposes a named **Retry refresh** action; retry performs only the read and never repeats the mutation.
- Navigation and close stop admitting those immediate actions, announce that accepted changes are finishing, and continue only after the valid draft and accepted action queue settle. Invalid or failed drafts retain the existing save, discard or stay decision before the queue can continue.
- Category editing includes a keyboard-operable named-colour selector and live marker-and-name preview. The colour is part of the same explicit draft and dirty-navigation decision as the Category name.
- New Project and Task actions open a transient inspector without permanent Create or Cancel buttons. The first valid automatic save creates the item; blank or incomplete drafts can be left without adding a partial record.
- New Task defaults reflect its launch surface and remain visible and editable: a Project supplies attachment and inherited Category; a Category supplies a standalone Category; Today supplies Today membership and Planned while allowing optional Project selection; Backlog and global creation default to standalone and require a Category.
- Each Project includes an inline Quick add task field. Enter or Tab on a non-empty title creates an attached title-only Task and focuses a fresh field; Tab on an empty field exits normally, and Escape clears unsubmitted text. Created rows can be selected for full inspector editing.
- Backlog offers the same quick-add flow for standalone Tasks, with a required Category selector whose selection is retained only for the current rapid-entry session.
- Existing Task and Project inspectors place a neutral **Duplicate** action in an **ACTIONS** section before the recoverable Bin action. Its accessible name states the source type and that the result is new active work. Bin rows remain restore-only.
- Task duplication is immediate after pending valid edits flush, then opens the new Task and focuses its `Copy of` title. A Task from an archived Project becomes standalone rather than remaining attached to unavailable work.
- Project duplication opens the shared blocking decision overlay. The first field is the editable `Copy of` title, followed by the included Task count and explicit archived/Bin exclusion counts; Duplicate Project confirms, Cancel or Escape returns focus to the inspector action. Successful creation opens the new Project and focuses its title.
- Project status and completion date are read-only derived fields.
- An active, incomplete Project past its target date shows a warning icon with accessible Overdue text on its row. The Projects navigation item does not show an overdue badge.
- Task Category indicates inherited versus overridden state.
- The Participant picker ends with **New participant…**. Selecting it reveals and focuses a temporary label field; Enter or Add creates and associates a unique label, reuses an equivalent existing Participant, or reports that the Participant is already on the Task. Escape or Cancel closes the field and returns to the picker.
- Participant rename and delete do not appear in each Task inspector. A count-free **Settings** utility destination remains at the bottom of navigation. Its **AI features** section owns an accessible device-local **Enable AI features** switch which is off by default and explains that enabling local provider-neutral tools neither contacts a provider nor shares workspace data. Its Appearance section offers an accessible selector for the built-in dot-orbit, Monokai Classic, Dracula Classic, Alucard Classic, Catppuccin, and Gruvbox themes, applies the choice immediately across application windows, and remembers its stable identifier on the device. Its Participants section uses the shared list panel and row recipes, shows usage counts, and makes only the active rename row editable with Save/Cancel. Its Data export section launches a focused modal that previews active and archived record counts, states that Bin is excluded, requires an explicit JSON destination, and asks for final confirmation that the output is unencrypted before writing. It never suggests the configured recovery directory, and cancellation writes nothing. Its Recovery section launches the existing recovery window; there is no permanent Recovery action in the top bar. Its Security section launches a focused passphrase-change window that requires the current passphrase, repeats creation guidance and the no-recovery warning, and keeps existing recovery points under the passphrase that created them. Successful rotation returns to Settings and shows a visible, polite live confirmation that the new passphrase will be used at the next unlock.
- **About and updates** is the first Settings section. It keeps installed-version identity, privacy disclosure, automatic-check toggle, update status, **Check now**, **View release notes and downloads in browser**, and **Dismiss this version** in one reading and Tab order. Checking starts only after the unlocked main window is usable and never steals focus. Fixed status copy is politely announced. An available official update adds a count-free **Update** pill to the existing Settings navigation item; its accessible status is `Application update available`. **Dismiss this version** removes only that pill for the exact release and leaves the verified release details and fixed, locally constructed browser action visible. Unsupported development builds never show the pill or check automatically, while manual checking can show the latest stable release in the section.
- The AI-features section reveals a subordinate, independently off-by-default **Enable local MCP** row only while the global gate is on. The row is vertically centred, keyboard operable, exposes its current state accessibly, and warns that approved same-user software can read sensitive plaintext current-work context and submit untrusted proposals but cannot approve or apply them. Fixed stopped/running/error status is announced politely. Turning the global gate off atomically persists MCP off and removes all subordinate controls from visual, focus, and accessibility traversal.
- Beneath the MCP switch, Settings lists remembered clients by explicitly unverified display name, verified operating-system account, and exact human-readable scopes. Each row has a named **Revoke** action. A new connection opens a focused modal whose initial focus is **Deny**; verified connection facts and unverified name/version occupy separate labelled panels, requested scopes and powers are stated in full, and **Allow once** is visually subordinate to remembered **Always allow** without making either the safe default.
- An accepted inbound proposal never navigates, opens Review, or steals focus. The AI navigation item gains a prominent accessible `Review N` indicator and a polite, dismissible in-app banner announces the arrival without proposal content. Restored queue items do not replay the banner. Selecting AI exposes an accent-coloured aggregate queue summary and one fixed-height, vertically centred, content-free row per proposal in stable arrival order, separate from the still-editable manual editor. A row's **Review** action opens the ordinary modal proposal Review dialog; its added **Source** section distinguishes **Text / JSON import**, **JSON file import**, and a self-reported `<client> via local MCP` label. When unrelated Workspace changes have occurred since a queued Change proposal arrived, Review shows a compact **Preview refreshed** notice and the newly calculated current-to-proposed effects. If related work changed or an older row has no compatibility basis, the proposal remains pending and fixed non-sensitive guidance appears beneath the counts in the aggregate summary, where it is announced politely without changing row geometry. While AI is already selected, the arrival banner's **Review** action opens the oldest queued proposal; from another destination it selects AI and focuses that row. Explicit discard removes only that row and returns focus to the next row or the manual editor.
- When AI features are enabled, a count-free **AI** utility destination with the approved sparkle icon sits immediately above Bin. While disabled it is absent from visual, focus, and accessibility traversal and cannot be selected programmatically. Its introduction says that dot-orbit does not contact an AI provider. **Bring work into dot-orbit** is the primary flow: one compact, bounded proposal editor accepts typing, explicit **Paste**, **Load from file…**, or one dropped ordinary local file. A New-work proposal can add an entirely new local graph without workspace context. **Share workspace context (optional)** follows below and is required only when an agent must update or connect existing work. Paste, file load, and drop replace and display the complete editor contents; every rejected replacement preserves the existing editor contents.
- AI owns the operational interchange list/action rows and visible status; Settings owns availability but does not duplicate those actions or outcomes. Disabling AI features cancels proposal intake and discards in-memory proposal and review authority. **Review and copy…** first obeys the inspector save/discard/stay contract, then retains one atomic Planning snapshot for the lifetime of a focused review window. The review names every included record type and relationship, gives exact Category, Participant, active Project, included Task, completed Task, and excluded archived-child counts, states the archived/Bin and non-workspace exclusions, and warns that the complete reusable catalogue may reveal names or labels referenced only by hidden work. Its assertive confirmation states that sensitive unencrypted plaintext will enter clipboard history and authorises one copy only. Cancel, close, navigation, or global disable does not write; completion returns focus to the launcher and fixed non-sensitive status text is announced.
- Within the enabled AI destination, an enabled-by-default device-local **Include agent instructions and schema with snapshot** switch controls composition without enabling AI features itself. Enabled snapshot copies produce one documented provider-neutral text payload containing role, constraints, exact immutable v2 schemas (explicit v1 resources remain supported), operation vocabulary, output instructions, and the retained snapshot. Disabled copies contain only pretty-printed snapshot JSON; the combined document uses the same formatting for its snapshot portion. **Copy instructions** copies the reusable material without reading workspace content and does not require live-snapshot confirmation. Every path writes only plain text, measures the complete strict-UTF-8 output against 16 MiB before clipboard access, never truncates, and reports a fixed failure when over limit.
- **Review proposal** validates the current text once and opens a modal review of the resulting immutable plan. The review leads with the proposal type, human counts, and target names, and lists only records directly created or changed. New Projects are the parent rows of their new Tasks; new Tasks attached to an existing Project are grouped under that Project context; standalone Tasks and supporting Category or Participant identities remain separate. A mixed workspace-bound proposal places those rows under **New work** and separates them from **Existing changes**. Existing work is grouped once by stable record identity, with all of that record's direct changes kept in operation order. Project, Category, and Task rows reuse the shared coloured identity glyphs, Category marker, and Category/Project relationship pill. Participant rows keep `PERSON` and the name flush-left in one explicit text stack rather than introducing an unapproved avatar glyph. A Task Category override is named visibly beside a branch glyph without an arrowhead; the Category grid and Project cards remain separate identity markers. The preview uses the same deterministic Category and Project colour assignment as application. Explicit v2 Today additions, lane moves, and removals appear as direct Task changes with current and proposed lane text. Their accessible names identify the Task and both states. Routine ordering, inheritance, lifecycle-driven Today removal, aggregate, and derived-status consequences are described once as implied instead of expanding otherwise untouched records into review rows. Source identity and revision where applicable, validation counts, and excluded powers remain available under **Technical details**. The review's kind-specific **Add new work** or **Apply changes** action is the explicit whole-proposal approval and immediately enters the recovery, final stale-check, and atomic Apply pipeline without a second confirmation overlay. Closing review, changing the input, or ending the workspace session invalidates the plan; a committed maintenance failure offers maintenance retry without replaying operations.
- Markdown descriptions open as a rendered preview with semantic block spacing and an accessible name that includes the rendered plain-text content. Activating the preview with pointer, keyboard, or an accessibility Invoke action switches it to the source editor; moving focus away or clicking anywhere outside the editor returns to the rendered view without saving the inspector draft or stealing focus from the next control. Tab and Shift+Tab change Markdown list indentation; indenting a numeric or lower-alpha ordered item converts it to an unordered sub-point, while unordered markers and plain text retain their type. Enter continues the current marker outside code blocks, and Control+Tab preserves ordinary focus traversal. Ordered, unordered, and mixed nesting stays visibly distinct through at least four levels.
- **Copy rendered** writes `text/html` and `text/plain` clipboard formats.
- Approved absolute web and email links in the preview are pointer- and keyboard-operable. Unsafe destinations and local fragments without a preview navigation target remain inert text.

## Project status presentation

- Project rows omit a separate status word; their accessible name still announces the textual status.
- Not started: neutral completed/total Task count.
- An empty Project is Not started and shows 0 of 0 Tasks with no completion date.
- In progress: amber completed/total Task count.
- Complete: green completed/total Task count and the derived final completion date.
- Expanded Project Task rows align the due date and exactly one current state in one fixed column: `Archived <date>` supersedes `Completed <date>`, which supersedes amber `⚠ Overdue`. Restore and Today remain in a compact adjacent action column. Project headers use the same date-then-state rhythm for completion or overdue.

## Responsive boundary

The first release is desktop-first. The inspector may become an overlay at narrower desktop widths, but mobile navigation and mobile editing are separate design work rather than compressed desktop UI.
